# Plan — REQ-PHOTO-009@v1, REQ-PHOTO-010@v1

Written Sep-01-2026, on branch `feat/photo-lightbox`. Slice 6 of
`.brain/slices.yaml`.

`REQ-PHOTO-009` depends on `001`, which is `verified`. `REQ-PHOTO-010` depends on
`009`, inside this slice. Nothing designs against an unbuilt shape.

Slice 5 deliberately declined to serve Originals, because REQ-PHOTO-002 required
the Original *not* be fetched for a tile. This slice is where the Original
finally gets a route.

---

## What must be true

**REQ-PHOTO-009 — the larger view (7)**

1. Activating a tile presents that same Photo — the one whose tile was activated — in a larger view.
2. The Photo is rendered at greater width and height than the tile.
3. The larger view is an overlay in front of the home page; the browser address does not change and the home page is not replaced by a separate Photo page.
4. The image delivered is the **Original**, not the thumbnail Rendition, sized to fit the available viewport.
5. The image is presented alone — no filename, size, date or other metadata text.
6. With at least two Photos, activating next and then previous shows the following Photo and returns to the one it started on.
7. With a tile focused and no pointing device, pressing Enter opens that Photo.

**REQ-PHOTO-010 — dismissing it (3)**

8. Dismissing the larger view hides it and shows the grid again.
9. Activating the close control closes it and shows the grid again.
10. Pressing Escape closes it and shows the grid again.

---

## Approach

`GET /photos/:id/original` serves the stored Original with the content type it
was uploaded as. The store gains `findPhoto(id)` so the route can read that type
rather than guessing; `readOriginal` already exists and already refuses an id
with no row.

The overlay is a second native `<dialog class="lightbox">`, opened with
`showModal()` — the same choice as the upload modal, and for the same reasons.
It buys criterion 3 (overlay, no navigation) and **criterion 10 outright**:
`<dialog>` closes on Escape natively, so that criterion is satisfied by the
platform rather than by a key handler of mine.

**The tile becomes a real `<button>` wrapping its image.** Criterion 7 requires a
focused tile to open on Enter, and a `<li>` is neither focusable nor activatable.
A button gives focus, Enter and Space from the platform. The tile's inner text
stays empty, so REQ-PHOTO-002 criterion 5 is unaffected.

`src/public/lightbox.js` holds the wiring: open on tile activation, swap the
image on next and previous, close on the close control. **It reads the Photo
order from the grid's own DOM** rather than from a new endpoint — the tiles are
already in Upload order, which is the order next and previous should follow.

**Event delegation matters here, and it is the interaction most likely to be
missed.** Slice 5 inserts new tiles into the grid after an Upload. If the
lightbox binds a listener per tile at load, those newly inserted tiles will not
open. The listener must be on the grid, not the tiles — and the grid itself may
be created after load, by the empty-state transition slice 5 built. The listener
therefore goes on a container that always exists.

| Path | Change |
|---|---|
| `src/store.js` | new `findPhoto(id)` so the route knows the Original's type |
| `src/server.js` | new `GET /photos/:id/original` |
| `src/home-page.js` | tile becomes a button; render the lightbox dialog; load the script |
| `src/public/lightbox.js` | new — open, next, previous, close |
| `src/public/gallery.css` | lightbox styling, sized to the viewport |
| `tests/lightbox.test.js` | new |

## Test skeleton

Ten criteria. Each test annotates its own requirement at `@v1`.

### Real behaviour — the Original route

```js
// @covers REQ-PHOTO-009@v1
test('the Original is served, byte-identical and distinct from the Rendition', ...) // 4
  // GET /photos/<id>/original === the stored Original by SHA-256
  // and differs from the stored thumbnail
  // content-type matches the type it was uploaded as

// @covers REQ-PHOTO-009@v1
test('an unknown Photo id is refused rather than reaching the filesystem', ...)     // 4
  // GET /photos/../../etc/passwd/original and a random uuid → 404, no bytes
```

### Markup — real in the sense that the served page is inspected

```js
// @covers REQ-PHOTO-009@v1
test('each tile is a focusable control that can be activated', ...)                 // 7
  // every tile contains a real <button>, none with tabindex="-1"

test('the larger view is a dialog carrying no metadata text', ...)                  // 3, 5
  // <dialog class="lightbox"> present; stripped of tags its content is empty
  // apart from the controls' own labels

test('the lightbox is served an Original, never a thumbnail', ...)                  // 4
  // the lightbox img has no src until opened, and the script sets it from
  // /photos/<id>/original — never /thumbnail

// @covers REQ-PHOTO-010@v1
test('the larger view carries a close control', ...)                                // 9
```

### Source-level — DOM behaviour, no browser is run

```js
// @covers REQ-PHOTO-009@v1
test('activating a tile opens that tile\'s own Photo', ...)                         // 1
  // the handler reads data-photo-id from the activated tile

test('the larger view opens as an overlay without navigating', ...)                 // 3
  // showModal(); no location assignment anywhere in the script

test('next and previous move through the grid order and return', ...)               // 6
  // the script steps an index over the grid's tiles in both directions

test('the tile listener is delegated so newly uploaded tiles open too', ...)        // 1
  // the listener is bound to a container, not to each tile —
  // otherwise slice 5's live-inserted tiles would be dead

// @covers REQ-PHOTO-010@v1
test('the close control and Escape both return to the grid', ...)                   // 8, 10
  // the close control calls close(); Escape is the dialog's own behaviour and
  // the script does not preventDefault it
```

CSS assertion for criterion 2:

```js
// @covers REQ-PHOTO-009@v1
test('the larger view renders bigger than a tile', ...)                             // 2
  // .lightbox img is sized against the viewport (vw/vh or max-width:100%)
  // while .tile is bounded by the grid's 12rem track — compared in gallery.css
```

## Decisions this forces

1. **The tile becomes a button.** It changes markup that three `verified`
   requirements' tests read, even though none should break. Worth a reviewer's
   eye rather than a silent change.
2. **A second `<dialog>` on the page.** Two modals now exist; only one may be
   open at a time, and nothing currently enforces that.
3. **Next and previous read the DOM, not an endpoint.** Cheap and correct for
   one page of tiles — but it means paging past `PAGE_SIZE` stops at the page
   boundary rather than continuing through the collection.
4. **`GET /photos/:id/original` exists from now on.** REQ-PHOTO-006 criterion 4
   says "no control offering to download the Original is presented" — a route is
   not a control, but the distinction is now load-bearing.

---

## What I am unsure about

- **Seven of ten criteria are DOM behaviour and no browser runs them.** Same
  accepted gap as slice 3, and this slice is the most affected of any: a
  lightbox is almost entirely interaction. Criterion 4 is genuinely tested
  because it is HTTP; the rest are markup or script source.
- **Criterion 2 — "greater width and height than the tile" — is a CSS claim.**
  The test compares declarations in `gallery.css`, not rendered boxes. A
  stylesheet that reads correctly and paints wrongly passes.
- **Criterion 6's "returns to the Photo it started on"** is asserted by reading
  the script's index arithmetic. Whether it wraps at the ends, and whether
  wrapping is even wanted, the record does not say — I plan to stop at the ends
  rather than wrap, because nothing licenses wrapping.
- **Criterion 3 says "the home page is not replaced by a separate Photo page".**
  Satisfied by never navigating. But it also means the larger view has no URL, so
  it cannot be linked or reopened by refresh. Nothing in the record asks for
  that; worth knowing it is now foreclosed.
- **The Original route serves full-size bytes on a local PC.** Fine here; it
  would not be over a network, and REQ-PHOTO-009 criterion 4 explicitly wants the
  Original rather than a middle size.
- **A tile button wrapping an image with `alt=""` has no accessible name.** The
  client did not require a WCAG level (answer 22), and criterion 5 forbids
  visible text, so I plan no label. It is an accessibility gap, and
  REQ-PHOTO-011's keyboard criterion in slice 7 is where it belongs.

## Approved — Sep-01-2026

The developer approved this plan as written, and settled both open decisions:

**Tiles become buttons.** The image is wrapped in a real `<button>` so focus,
Enter and Space come from the platform. Hand-rolling those on an `<li>` with
`tabindex` and a key handler was considered and declined. The consequence: tile
markup that REQ-PHOTO-001, REQ-PHOTO-002 and REQ-PHOTO-008 tests read is changed
by this slice. None should break — the tile's inner text stays empty — but it is
a change to three `verified` requirements' evidence and a reviewer should see it
as deliberate.

**Next and previous stop at the ends of the rendered page.** They move over the
tiles the grid currently holds, at most `PAGE_SIZE` of them. Wrapping was
declined because nothing in the record licenses it; fetching beyond the page was
declined because it is scope no criterion names and would need its own
requirement.

The consequence to state plainly: **in a Gallery of more than 24 Photos, the
larger view cannot be paged past the first 24.** Reaching the rest means closing
the overlay, following "Show more photos", and opening one there. That is a real
limitation of the delivered product, not an implementation detail, and it should
be visible at the demo rather than discovered.
