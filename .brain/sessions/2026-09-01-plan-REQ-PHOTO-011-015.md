# Plan — REQ-PHOTO-011@v1, REQ-PHOTO-015@v1

Written Sep-01-2026, on branch `feat/photo-responsive`. Slice 7 of
`.brain/slices.yaml` — the last one.

`REQ-PHOTO-011` depends on `001`, which is `verified`. `REQ-PHOTO-015` depends on
nothing. Every other requirement in the project is already `verified`.

**This is an audit slice, not a build slice**, and that shapes everything below.
Both requirements describe properties the earlier six slices were supposed to
have produced. Much of `REQ-PHOTO-011` is already true: slice 2's grid uses
`repeat(auto-fill, minmax(...))` with a `gap`, which is reflow and uniform
spacing. The job here is to *prove* it, and to fix only what proving it exposes.

Expect several tests to pass the moment they are written. That is the correct
outcome for an audit and will be reported as such rather than dressed up as work.

---

## What must be true

**REQ-PHOTO-011 — responsive and keyboard-reachable (4)**

1. At a common desktop viewport width in Chrome, Edge or Firefox, the grid reflows to fit and the document's scrollable width does not exceed the viewport width.
2. The "+ Upload Photo" control is visible within the viewport and activatable without horizontal scrolling.
3. Tiles are laid out with uniform spacing, and no tile overlaps another tile or the upload control.
4. Every control needed to upload a Photo and to open and close the larger view can be reached and activated from the keyboard alone.

**REQ-PHOTO-015 — the dependency list (2)**

5. Every declared third-party runtime dependency provides functionality not reasonably available from the Node.js standard library or the application's own code.
6. Each entry serves the web server, SQLite access or image thumbnail generation, and **no entry serves any other purpose**.

---

## Approach

### REQ-PHOTO-015 — genuinely checkable, and the strongest test in the slice

The project declares exactly two dependencies: `node-sqlite3-wasm` and `jimp`.
Criterion 6 is an allowlist, so the test *is* the allowlist:

```
APPROVED = {
  'node-sqlite3-wasm': 'SQLite access',
  jimp:                'image thumbnail generation',
}
```

The test asserts the declared set equals the approved set exactly. Adding any
dependency fails until someone records its purpose against one of the three the
client named — which forces the conversation rather than allowing quiet drift.
That is the audit, mechanised.

Criterion 5 is stronger than an assertion of good faith for the SQLite entry: the
test **proves** `node:sqlite` is unavailable on this project's Node floor by
importing it and requiring the failure. That is the actual justification, checked
rather than asserted. For `jimp` the justification is that Node ships no image
codec; the test asserts no `node:` builtin provides one, which is weaker and is
named as such.

The test also asserts `devDependencies` stays empty — the project has never had
one, and REQ-PHOTO-015 speaks only of runtime dependencies, so this is recorded
as a deliberate reading rather than a claim of coverage.

### REQ-PHOTO-011 — mostly already true, and mostly not provable here

Criteria 1, 2 and 3 are rendering claims. With no browser (REQ-PHOTO-015 forbids
the dependency), the tests assert the stylesheet declarations that produce those
outcomes:

- **Reflow and no horizontal overflow**: `grid-template-columns` uses
  `auto-fill`/`auto-fit` with `minmax`, so tracks shrink rather than overflow;
  no rule sets a fixed width wider than its container; images are bounded to
  `100%`.
- **Uniform spacing**: the grid sets a single `gap`, not per-tile margins, so
  spacing cannot vary between tiles.
- **No overlap**: nothing in the stylesheet uses absolute or fixed positioning
  inside the grid, and the tiles are ordinary grid items.

Criterion 4 is markup: every control needed to upload a Photo and to open and
close the larger view must be a real focusable element. All eight already are —
`.upload-control`, `.tile-open`, the file input, `.upload-submit`,
`.upload-close`, `.lightbox-previous`, `.lightbox-next`, `.lightbox-close`. The
test enumerates them and asserts none is a `div`, none carries `tabindex="-1"`.

**The one thing I expect to actually change** is a visible focus indicator.
`.tile-open` sets `border: 0; background: none`, and a tile is an image with no
text, so a keyboard user has no way to see which tile has focus. The criterion
says controls must be *reached and activated*, which is mechanically true
without a focus style — but a person who cannot see focus cannot use the
keyboard in practice. I propose adding `:focus-visible` outlines and am flagging
it as a judgement call rather than smuggling it in.

## Test skeleton

```js
// @covers REQ-PHOTO-015@v1
test('every declared dependency serves a purpose the client approved', ...)      // 6
  // declared deps === { node-sqlite3-wasm, jimp } exactly; no extras, none missing
  // devDependencies is empty

test('the SQLite dependency is not reasonably available from Node itself', ...)  // 5
  // importing node:sqlite on this engines floor throws — the justification,
  // proved rather than asserted

test('the thumbnail dependency is not reasonably available from Node itself', ...) // 5
  // WEAKER: no node: builtin provides an image codec

// @covers REQ-PHOTO-011@v1
test('the grid reflows rather than overflowing the viewport', ...)               // 1
  // CSS: auto-fill/auto-fit + minmax; no fixed width beyond its container;
  // images bounded to 100%

test('the upload control sits in normal flow, reachable without scrolling', ...) // 2
  // CSS + markup: the control is not absolutely positioned or off-canvas

test('tile spacing is uniform and no tile can overlap', ...)                     // 3
  // CSS: one gap on the grid, no per-tile margin, no absolute positioning

test('every control is a real focusable element', ...)                           // 4
  // all eight controls are <button> or <input>; none is a div;
  // none carries tabindex="-1"

test('keyboard focus is visible on every control', ...)                          // 4
  // CSS: a :focus-visible rule exists and is not outline:none
```

## Decisions this forces

1. **The approved dependency list lives in the test.** There is no
   `dependencies.md` and no custom `package.json` key; the assertion is the
   record. It means the list is enforced on every run rather than reviewed
   occasionally — and it means changing the list is a code change a reviewer
   sees.
2. **Only *declared* dependencies are audited.** Two direct entries pull in 65
   packages transitively. Criterion 6 says "declared", so that is what is
   checked; the transitive tree is not, and a reviewer should know that.
3. **Adding `:focus-visible` styling**, if approved — the only production change
   in the slice.

---

## What I am unsure about

- **Criteria 1, 2 and 3 are rendering claims verified by reading CSS.** This is
  the same accepted gap as slices 3 and 6, and here it is at its most acute: the
  requirement is literally about what a browser does at a given viewport width,
  and no browser runs. A stylesheet that reads correctly and paints wrongly
  passes every test in this slice.
- **"A common desktop viewport width" is never given a number.** The client named
  no width (answer 21 said desktop Chrome, Edge and Firefox; mobile and tablet
  out of scope). The tests therefore assert width-independent properties —
  `auto-fill` reflows at *every* width — which is arguably stronger than testing
  one number, but it is not what the criterion literally says.
- **Whether the focus indicator belongs in this slice at all.** Criterion 4 says
  "reached and activated", which is mechanically satisfied today. I read the
  intent as including *knowing* where focus is. If you disagree, drop it and the
  slice becomes pure audit with no production change.
- **Criterion 5 for `jimp` is the weakest assertion in the slice.** "Not
  reasonably available from the standard library" is a judgement, and the test
  can only show Node ships no image codec. For `node-sqlite3-wasm` the same
  criterion is genuinely proved.
- **After this slice every requirement is `verified` and none is `signed_off`.**
  That last transition is the client accepting delivered work, and no tool or
  agent may assert it. The project will be complete in the record's terms and
  still awaiting KCB.

## Approved — Sep-01-2026

The developer approved this plan as written, and settled both open questions:

**`:focus-visible` outlines are included.** Criterion 4 is read as requiring that
a keyboard user can *see* which control has focus, not merely that focus can
land there. This is the slice's only production change; everything else is
verification of what the earlier six slices already produced.

**The approved dependency list lives in the test.** `package.json` under a
custom key and `.brain/constraints/` were both considered and declined — the
first because npm ignores it and nothing would enforce it, the second because it
would couple test code to the record. Keeping it in the test means the list is
enforced on every run and any change to it appears in a diff a reviewer reads.

The consequence to remember: **the approved dependency list is not written in
`.brain/`.** Someone looking for the client's dependency agreement will not find
it in the record; it lives in `tests/dependencies.test.js`. That is a deliberate
trade of discoverability for enforcement.
