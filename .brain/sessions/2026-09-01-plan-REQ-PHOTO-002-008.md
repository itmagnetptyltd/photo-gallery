# Plan — REQ-PHOTO-002@v1, REQ-PHOTO-008@v1

Written Sep-01-2026, on branch `feat/photo-thumbnails`. Slice 5 of
`.brain/slices.yaml`.

`REQ-PHOTO-002` depends on `001`; `REQ-PHOTO-008` depends on `001` and `006`.
**All three are `verified` and on this branch**, so for the first time this slice
designs against code that exists rather than code a sibling slice will choose.

This is the slice that makes the grid actually show photographs. Slice 4 stores
Originals and generates Renditions; nothing serves them, so every tile is
currently a grey square pointing at a 404.

---

## What must be true

**REQ-PHOTO-002 — tiles show the Rendition, not the Original (6)**

1. A Photo whose Original is larger than a tile is rendered at the tile's dimensions, not the Original's pixel dimensions.
2. Every tile's image request returns a successful response carrying image data; no tile shows a broken or placeholder image.
3. A JPEG Original and a PNG Original both render.
4. The image delivered for a tile is the **thumbnail Rendition**, smaller in bytes than the Original, and **the Original is not requested for the tile**.
5. A tile presents the image alone — no filename, size, date or other metadata text.
6. With more Photos held than fit one screen, Renditions are requested only for the tiles presented, not for every stored Photo.

**REQ-PHOTO-008 — a new Photo appears without a reload (3)**

7. With the home page open showing N tiles, a completed Upload leaves the grid showing N+1, one of them the new Photo, without the person reloading.
8. The new tile appears in the uploading person's own open grid without a full page reload; no other person's open grid need update.
9. With the grid ordered most recent Upload first, the new tile appears in **first position**.

---

## Approach

**Serving Renditions.** `src/server.js` gains `GET /photos/:id/thumbnail`,
answering with the stored Rendition. `src/store.js` currently hands every Photo
an `imageUrl` of `/photos/<id>/image` — a placeholder slice 2 invented and
nothing ever served. It becomes `thumbnailUrl`, pointing at the new route, and
`src/home-page.js` renders that. **No route for the Original is added**:
criterion 4 requires the Original *not* be fetched for a tile, and serving it is
`REQ-PHOTO-009`'s business in slice 6.

**Inserting without a reload.** Slice 2 chose server-side rendering, and slice 2's
plan predicted this moment: `REQ-PHOTO-008` needs client-side JavaScript and
something for it to call. Rather than teach the browser to build tile markup —
which would put tile HTML in two places that can drift — **`POST /uploads` answers
`201` with the rendered tile fragment as `text/html`**, and the client prepends
it. One renderer, server-side, and the client stays wiring.

`src/home-page.js` exports `renderTile` so the same function produces the tile in
the grid and in the upload response.

The empty-state case matters: with no Photos there is no `.gallery-grid` to
prepend to, so the first Upload must create one. That is criterion 7 with N = 0,
and it is the case most likely to be missed.

| Path | Change |
|---|---|
| `src/server.js` | new `GET /photos/:id/thumbnail`; `POST /uploads` returns the tile fragment |
| `src/store.js` | `imageUrl` becomes `thumbnailUrl` |
| `src/home-page.js` | export `renderTile`; tiles use `thumbnailUrl` |
| `src/public/upload-modal.js` | prepend the returned fragment; create the grid when empty |
| `src/public/gallery.css` | styling for the empty-to-grid transition, if needed |
| `tests/support/png.js` | add a JPEG fixture for criterion 3 |
| `tests/tiles.test.js` | new — REQ-PHOTO-002 |
| `tests/live-insert.test.js` | new — REQ-PHOTO-008 |

## Test skeleton

Nine criteria. Each test annotates its own requirement at `@v1`.

### REQ-PHOTO-002 — mostly real, because it is HTTP rather than DOM

```js
// @covers REQ-PHOTO-002@v1
test('the tile image is rendered at tile size, not the Original size', ...)      // 1
  // decode the served Rendition; width === THUMBNAIL_EDGE and < the Original's

test('every tile image request succeeds and carries image data', ...)            // 2
  // parse each tile's src from the markup, fetch it: 200, image content-type,
  // non-empty body. No tile may 404 — the state this slice exists to end.

test('a JPEG Original and a PNG Original both render', ...)                      // 3
  // store one of each; both tiles fetch successfully

test('the tile is served the Rendition and never the Original', ...)             // 4
  // served bytes === the stored thumbnail, and are smaller than the Original
  // the tile src does not point at any Original route

test('a tile presents the image alone', ...)                                     // 5
  // no filename, no size, no date text inside the tile element

test('Renditions are requested only for the tiles presented', ...)               // 6
  // store more than PAGE_SIZE; the markup carries exactly PAGE_SIZE thumbnail
  // URLs, not one per stored Photo
```

### REQ-PHOTO-008 — DOM behaviour, so weaker

```js
// @covers REQ-PHOTO-008@v1
test('a completed Upload returns a tile the page can insert', ...)               // 7
  // REAL: POST /uploads answers 201 with text/html whose body is a tile
  // carrying the new Photo's data-photo-id

test('the client inserts the returned tile without reloading', ...)              // 8
  // SOURCE-LEVEL: the script inserts the response body into the grid and
  // contains no reload or navigation. No browser is run.

test('the new tile is inserted in first position', ...)                          // 9
  // SOURCE-LEVEL: the script prepends. Also REAL in part — a fresh page
  // request after the Upload shows the new Photo first, which is the same
  // ordering guarantee from a different direction.
```

---

## Decisions this forces

1. **`POST /uploads` returns HTML, not JSON.** It keeps one renderer and stops
   tile markup existing in two places. The cost is an upload endpoint that
   answers with a fragment, which is unusual and worth recording.
2. **`thumbnailUrl` replaces `imageUrl`.** The slice-2 placeholder is retired
   rather than quietly repurposed, so nothing reads as if an Original were being
   served.
3. **No Original route yet**, deliberately, so criterion 4 cannot be
   accidentally satisfied by serving the wrong thing.
4. **The empty state becomes a grid client-side.** Two renderings of "no Photos
   yet → one Photo" now exist: the server's, and the client's transition.

---

## What I am unsure about

- **Criteria 7, 8 and 9 are DOM behaviour and no browser is run.** Same accepted
  gap as slice 3. Criterion 7 is genuinely testable because the fragment is an
  HTTP response; 8 and 9 are assertions about script source. The insert is
  verified by a person or not at all.
- **The JPEG fixture will be generated with `jimp`** — the same library the
  thumbnail generator uses. A bug inside `jimp` could therefore mask itself in
  criterion 3. Hand-writing a JPEG encoder for a test is not proportionate, but
  the weakness is real and I would rather name it than hide it.
- **Criterion 6 says Renditions are "requested only for the tiles presented".**
  The test counts thumbnail URLs in the served markup, which proves the page does
  not *ask* for more. It does not prove a browser fetches only what is visible —
  lazy loading below the fold is a different claim, and not one this criterion
  makes.
- **Criterion 1 says "rendered at the tile's dimensions".** The test asserts the
  served Rendition's pixel width, which is the part the server controls. What a
  browser paints is CSS, and unverifiable here.
- **`GET /photos/:id/thumbnail` takes an id straight from the URL.** The store
  looks the id up in SQLite before touching disk and builds the path itself, so a
  traversal attempt cannot reach outside the data directory — but this is the
  first route that accepts caller-supplied input into a file path, and it
  deserves a reviewer's eye.
- **Slice 4's `imageUrl` disappears.** Nothing in a `verified` requirement's
  tests reads it, so no evidence should need editing — but if any does, that is a
  finding rather than something to quietly fix.

## Approved — Sep-01-2026

The developer approved this plan as written, and confirmed decision 1: **`POST
/uploads` answers with the rendered tile fragment as HTML.**

JSON with a client-side tile builder was considered and declined, because it
would put tile markup in both `home-page.js` and `upload-modal.js` where the two
can drift. A JSON response plus a second request for the fragment was also
considered and declined for the extra round trip.

The consequence to remember: the upload endpoint answers with a fragment rather
than a resource representation, which is unusual and will look wrong to anyone
reading it as a conventional API. It is deliberate, and the reason is one
renderer.
