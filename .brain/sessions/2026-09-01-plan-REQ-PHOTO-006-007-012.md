## The decision this slice cannot avoid

The client said, in answer 24: *"Photos are stored on disk and their metadata is
stored in SQLite."* `REQ-PHOTO-015` permits dependencies that serve "SQLite
access and image thumbnail generation". So both are sanctioned.

**But Node's built-in `node:sqlite` does not exist on the Node version this
project is pinned to.** Checked on the machine:

```
node v20.17.0   engines.node: ">=20.0.0"
require('node:sqlite') -> ERR_UNKNOWN_BUILTIN_MODULE
```

`node:sqlite` arrived in Node 22.5. Two ways forward, and they are not
equivalent:

**A. Take a SQLite dependency, keep the Node 20 floor.**
Explicitly permitted by REQ-PHOTO-015 and by answer 26. Changes nothing already
`verified`. Costs one dependency, and if it is a native module it needs a
toolchain on the PC — which brushes against REQ-PHOTO-014's "nothing else has
been prepared". A WASM build avoids the toolchain at some speed cost.

**B. Raise `engines.node` to `>=22.5.0` and use the built-in.**
No dependency at all, which serves "avoid unnecessary dependencies" best. **But
`REQ-PHOTO-013` and `REQ-PHOTO-014` are already `verified` against the Node 20
floor, and `tests/boot.test.js` asserts the running version satisfies
`engines.node`.** Raising the floor changes what those requirements mean. That is
a requirement version bump and a `CHG-` record, not an edit — and the client said
"a current Node.js LTS release", which Node 22 is, so it is defensible but it is
theirs to confirm.

The same fork applies to **thumbnail generation**: Node has no image codec, so a
Rendition needs a dependency. That one is unambiguous — REQ-PHOTO-015 names it —
but which library, and whether a native build is acceptable on a bare PC, is the
same question in a different coat.

**This plan assumes A unless told otherwise**, because it disturbs nothing that
is already `verified`. Everything below is written against that assumption and is
cheap to redirect.

### Resolved — Sep-01-2026

The developer chose **option A: take a SQLite dependency and keep the Node 20
floor**, and chose **pure-JS or WASM over native** for thumbnail generation.

Consequences, recorded so nobody has to re-derive them:

- `REQ-PHOTO-013` and `REQ-PHOTO-014` are **untouched**. `engines.node` stays
  `>=20.0.0`, no requirement version is bumped, and no `CHG-` record is needed.
- Both dependencies must avoid a native build, so `REQ-PHOTO-014`'s "nothing
  else has been prepared" still holds on a bare Windows PC with only Node
  installed. That rules out `better-sqlite3` and `sharp`.
- The two dependencies serve **SQLite access** and **image thumbnail
  generation** — exactly two of the three purposes `REQ-PHOTO-015` names. Its
  acceptance criteria remain satisfiable, and slice 7 verifies that.
- These are the **first dependencies in the project**. `tests/boot.test.js`
  asserts `package.json` declares none, so that test must change — a slice-1
  `verified` requirement's evidence edited by slice 4. Deliberate, and a reviewer
  should see it as such.

Library selection is deferred to `/tdd`, where availability and the absence of a
native build step will be confirmed before either is added.

## What must be true

**REQ-PHOTO-006 — a submitted file becomes a Photo (6)**

1. An acceptable image submitted and completed increases the Photo count by exactly one.
2. After a completed Upload, a fresh home page request presents the new Photo.
3. The same file uploaded twice yields **two** Photos and two tiles, not one.
4. The stored Original is byte-identical to the chosen file, and no download control is presented.
5. A thumbnail Rendition smaller than the Original has been generated and stored.
6. When disk space is exhausted, the Upload fails with a message and leaves no Photo record and no partial file.

**REQ-PHOTO-007 — a failed Upload (4)**

7. A failure shows a message in the modal and the modal does not close by itself.
8. A failure leaves the Photo count unchanged.
9. After a failure the person can submit the same file again without reopening the modal.
10. A failure part-way through writing leaves no Photo record and no partial file.

**REQ-PHOTO-012 — persistence (5)**

11. A Photo uploaded in an earlier browser session is present in a new session with no retained client state.
12. A Photo uploaded before the application was stopped is present after it is started again.
13. A Photo uploaded before the PC was shut down is present after the PC and application are started.
14. The stored Original from an earlier session is byte-identical to the file chosen then.
15. A removed Photo is absent in a later session, and the application offers no means of recovering it.

## Approach

`src/store.js` owns persistence: a SQLite database for Photo metadata and a
directory of files on disk, exactly as answer 24 describes. It exposes
`savePhoto({ bytes, filename, type })`, `listPhotos({ limit, offset })`,
`countPhotos()`, `readOriginal(id)` and `readThumbnail(id)`.

`src/photos.js` keeps the interface slice 2 depends on and delegates to the
store instead of an in-memory array. **`seedPhotos` is removed** — it was a test
seam justified by the store not existing, and it now does. Slice 2's tests seed
through the store instead, against a temporary database per test.

`src/thumbnails.js` generates the Rendition from an Original and returns bytes.
One place, so slice 5 can serve them without knowing how they are made.

**Atomicity is the design's centre of gravity**, because criteria 6, 10 and 15
are all about what must *not* be left behind. The order is: write the Original to
a temporary file in the same directory, generate the thumbnail, `fsync` and
`rename` both into place (atomic within a filesystem), then insert the metadata
row last. The row is the commit point — a file with no row is invisible and
collectable; a row with no file must never exist. Any failure before the insert
unlinks whatever temporary files exist. `savePhoto` takes an injectable failure
hook so criteria 6 and 10 can be tested without filling a disk.

`src/server.js`: `receiveUpload` calls `savePhoto` and answers `201 Created` on
success instead of `202 Accepted`, or a failure status the modal can show. The
client script gains no new rules — the message it renders on failure already
exists from slice 3.

| Path | Change |
|---|---|
| `src/store.js` | new — SQLite metadata, files on disk, atomic save |
| `src/thumbnails.js` | new — Rendition generation |
| `src/photos.js` | changed — delegates to the store, `seedPhotos` removed |
| `src/server.js` | changed — `receiveUpload` stores; `201` replaces `202` |
| `tests/grid.test.js` | changed — seeds through the store, not the removed seam |

| `tests/upload-store.test.js` | new |
| `package.json` | changed — first dependencies, under REQ-PHOTO-015's allowance |
| `README.md` | changed — where data lives, how to reset it |

## Test skeleton

Fifteen criteria. Each test annotates its own requirement at `@v1`.

### Real behaviour — the majority, and the reason this slice is testable

```js
// @covers REQ-PHOTO-006@v1
test('a submitted image becomes exactly one Photo', ...)               // 1
test('a completed Upload appears on a freshly requested home page', ...) // 2
test('the same file uploaded twice becomes two Photos', ...)            // 3
test('the stored Original is byte-identical to the file submitted', ...) // 4
  // sha256(stored) === sha256(sent); assert no download control in markup
test('a thumbnail Rendition smaller than the Original is stored', ...)   // 5
  // thumbnail exists, byte length < Original, and decodes as an image
test('a save that fails on disk leaves no record and no partial file', ...) // 6
  // inject failure at the write step; assert count unchanged AND the
  // storage directory contains no leftover temporary file

// @covers REQ-PHOTO-007@v1
test('a failed Upload leaves the Photo count unchanged', ...)           // 8
test('a failure part-way through writing leaves nothing behind', ...)   // 10
  // inject failure AFTER the Original is written but BEFORE the row is
  // inserted — the case a naive implementation gets wrong

// @covers REQ-PHOTO-012@v1
test('a Photo is present in a new session with no client state', ...)   // 11
test('a Photo survives the application being stopped and started', ...) // 12
  // close the store, reopen it against the same directory, assert present
test('the stored Original from an earlier session is byte-identical', ...) // 14
test('a removed Photo is absent later and cannot be recovered', ...)    // 15
  // delete via the store, reopen, assert absent and no recovery route
```

### Weaker or manual — stated, not hidden

```js
// @covers REQ-PHOTO-007@v1
test('a failure shows a message and the modal does not close itself', ...) // 7
  // SOURCE-LEVEL: the client renders the failure message and does not call
  // close() on a non-ok response. No browser is run.
test('the same file can be resubmitted without reopening the modal', ...)  // 9
  // SOURCE-LEVEL: the submit handler clears no file input on failure.

// @covers REQ-PHOTO-012@v1
test('a Photo survives the PC being shut down', ...)                       // 13
  // MANUAL: a process restart against the same directory is the closest
  // automatable proxy and is what this test actually does. A real power
  // cycle is never exercised by this repository.
```

## Decisions this forces

1. **SQLite access: dependency versus a Node 22.5 floor.** The fork above. It is
   the first question, and it decides whether this slice touches two `verified`
   requirements.
2. **Which thumbnail library, and whether a native build is acceptable** on a PC
   where "nothing else has been prepared" (REQ-PHOTO-014 criterion 2).
3. **Where the data directory lives**, and whether it is configurable. Nothing in
   the record says.
4. **The commit point is the metadata row.** Files first, row last. It is what
   makes criteria 6, 10 and 15 satisfiable, and it means orphaned files are
   possible after a crash while orphaned rows are not.
5. **`201 Created` replaces `202 Accepted`.** Slice 3's code is changed by slice
   4, which is expected but worth recording.
6. **Removing `seedPhotos`** changes slice 2's tests. They are `verified` against
   `REQ-PHOTO-001@v1`; the requirement is untouched, but its tests are edited,
   and a reviewer should see that as deliberate.

## What I am unsure about

- **The SQLite fork is not mine to settle.** It is the one thing I want decided
  before a test is written, because option B bumps two `verified` requirements
  and needs a `CHG-` record.
- **Criterion 13 (PC shut down) cannot be automated.** The test restarts the
  process against the same directory, which is the closest honest proxy. A power
  cycle mid-write — the case that actually threatens a store — is never
  exercised.
- **Criterion 6 says "disk space is exhausted".** Genuinely filling a disk is not
  something a test should do. Fault injection at the write boundary is the
  substitute, and it proves the cleanup path, not the disk-full path.
- **Criterion 15 needs removal, which still has no requirement.** Answer 17
  described delete with confirmation and permanent file removal, and no
  requirement was ever written for it. This slice needs *some* removal capability
  in the store to satisfy 15. I plan the store function and no user-facing
  control — the control is unowned scope, and inventing it here would be worse
  than leaving the gap visible.
- **Slice 2's tests change.** Unavoidable once the seam it used is removed, but
  it means a `verified` requirement's evidence is edited by a later slice.
- **Renaming across filesystems is not atomic.** If the temporary directory and
  the data directory ever differ, the guarantee behind criteria 6 and 10 quietly
  weakens. The plan keeps them in one directory; a reviewer should check that
  stays true.
