# Plan — REQ-PHOTO-013@v1, REQ-PHOTO-014@v1

Written Sep-01-2026, on branch `feat/photo-boot`.

**Scope note.** `REQ-PHOTO-014` depends on `REQ-PHOTO-013`, which is still at
`agreed`. That is normally a reason to stop and plan the dependency first, but
both are in this slice and are built together, so nothing here designs against a
shape an earlier slice has not chosen yet.

This is the boot slice. It serves a home page and nothing else. No Photo, no
Upload, no grid — those are `REQ-PHOTO-001` onward and are deliberately absent.

---

## What must be true

**REQ-PHOTO-013 — the application runs on the Node.js runtime**

1. On a machine where Node.js is the only installed language runtime, the
   documented start procedure starts the application and it serves the home
   page, with no other language runtime installed.
2. On a Windows PC with a current Node.js LTS release, the documented start
   procedure starts the application and it serves the home page.

**REQ-PHOTO-014 — the application starts and serves the home page on a single
local development PC**

3. From a clean checkout on a local development PC with the agreed
   prerequisites, the documented start procedure makes the home page reachable
   from a browser on that same PC, returning a successful response.
4. On a Windows PC with a current Node.js LTS installed and nothing else
   prepared, the documented install command followed by the documented run
   command makes the home page reachable, with no database server, container
   runtime or cloud service required.
5. With the application running on one local development PC, one person using it
   from a browser on that PC is served, and no capability for several people
   using it at the same time is required.

---

## Approach

A single HTTP server built on `node:http`, serving one static home page from
disk. No runtime dependency of any kind: criterion 4 forbids a database server,
container runtime and cloud service, and `REQ-PHOTO-015` requires every declared
dependency to provide something not reasonably available from the Node.js
standard library. A web server is available from the standard library, so this
slice declares none. Later slices may add SQLite access and thumbnail generation
under `REQ-PHOTO-015`'s allowance; this one must not pre-empt them.

The server binds to `127.0.0.1` rather than `0.0.0.0`. Criterion 5 says the
application serves one person on one PC and that concurrent multi-user access is
out of scope, and loopback-only binding is the observable form of that: it is
falsifiable by the other reading, because a server reachable from another
machine on the network fails it.

`createServer()` is exported separately from the code that listens, so tests can
bind an ephemeral port (`port 0`) instead of contending for a fixed one.

Files created:

| Path | Why |
|---|---|
| `package.json` | Root. `name`, `private`, `type: module`, `engines.node`, and the `start` and `test` scripts that criterion 4 calls "the documented run command". npm reads it from the working directory. |
| `src/server.js` | `createServer()` returning an `http.Server`, and `start()` which listens on loopback. Runs directly when invoked as the entry point. |
| `src/public/index.html` | The home page. A placeholder heading and nothing more — `REQ-PHOTO-001` replaces its body with the grid. |
| `tests/boot.test.js` | The five tests below, run by `node --test`. |
| `README.md` | Root. The documented install and run commands. Criterion 4 is unverifiable without it — "the documented install command" has to point at something. |

Nothing else goes at the root. No `public/`, no `lib/`, no `app/`.

**Side effect worth knowing.** Adding `package.json` at the root makes the
`javascript` adapter match (`detect: **/package.json`, and there is no
`tsconfig.json` to suppress it). That flips the `language adapter` gate, which
has failed since install, and gives `check-traceability` test files to scan for
the first time.

## Test skeleton

`tests/boot.test.js`, using the built-in `node:test` runner — the adapter's own
`testFiles` command is `node --test`, and a third-party runner would be a
dependency `REQ-PHOTO-015` does not allow.

```js
// @covers REQ-PHOTO-013@v1
test('starts and serves the home page with Node as the only language runtime', ...)
  // start the app under node alone; GET / returns 200
  // assert package.json declares no runtime dependencies, so nothing outside
  //   Node is needed to run it

// @covers REQ-PHOTO-013@v1
test('runs on a current Node.js LTS release', ...)
  // assert process.version satisfies the engines.node range in package.json
  // GET / returns 200 on that runtime

// @covers REQ-PHOTO-014@v1
test('home page is reachable from the same PC and returns a successful response', ...)
  // GET http://127.0.0.1:<port>/ returns 200
  // content-type is text/html

// @covers REQ-PHOTO-014@v1
test('starts from a clean checkout with no database server, container runtime or cloud service', ...)
  // assert package.json has no dependencies and no optionalDependencies
  // assert no Dockerfile, compose file or service-manifest exists in the repo
  // server reaches listening state without contacting any external host

// @covers REQ-PHOTO-014@v1
test('serves one person on that PC and is not reachable from another machine', ...)
  // assert the listening address is 127.0.0.1, not 0.0.0.0 and not ::
  // one sequential request returns 200
```

Five tests, five acceptance criteria, one each. Every test carries its
requirement at `@v1`.

## Decisions this forces

Each is a real choice between alternatives and needs an ADR once made. None
should be settled silently inside this slice.

1. **`node:http` instead of Express or Fastify.** Driven by `REQ-PHOTO-015`, but
   it is still a choice, and it is the one a later slice is most likely to want
   to reverse once routing and multipart upload arrive (`REQ-PHOTO-005`).
2. **Binding to loopback only.** Derived from answer 3. It makes the application
   unreachable from another device by design; if KCB ever wants to view the
   gallery from a phone, this is the decision that blocks it.
3. **ES modules (`type: module`) over CommonJS.**
4. **How the port is chosen and configured**, and what happens when it is already
   in use.
5. **The `engines.node` floor.** "A current Node.js LTS release" is a moving
   target with no date attached; pinning a range fixes a meaning the client gave
   loosely.

The SQLite decision from answer 24 is *not* forced by this slice and should not
be made here, but it is still outstanding and belongs in `decisions/` before
`REQ-PHOTO-012` is planned.

## What I am unsure about

- **Criterion 2 and criterion 4 are Windows-specific, and CI is not Windows.**
  The adapter's `ci.container` is `node:20-bookworm`, which is Linux. The gates
  can prove the application starts and serves on Node; they cannot prove it does
  so *on a Windows PC*. That half of both criteria is only ever verified by a
  person running it on Windows. I have written the tests to assert what is
  actually checkable and I am flagging the gap rather than papering over it with
  a test that would pass anywhere.
- **`node:20-bookworm` may not be "a current Node.js LTS" for long.** The CI
  container and `engines.node` can drift apart, and the requirement's wording
  will not notice.
- **"The documented start procedure" is circular until the README exists.** Both
  requirements lean on documentation this slice is also creating, so the tests
  verify the commands work, not that the prose is accurate. A wrong README with
  right scripts still passes.
- **The home page is a placeholder.** `REQ-PHOTO-001` will replace its contents
  entirely. If its markup shape turns out to constrain the grid slice, that is
  this plan's fault and the grid slice should feel free to discard it.
- **Criterion 4's "no cloud service required" is asserted negatively.** Absence
  of a Dockerfile and of declared dependencies is evidence, not proof; nothing
  stops later code from making an outbound call.
