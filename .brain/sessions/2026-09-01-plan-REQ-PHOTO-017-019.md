## What must be true

### REQ-PHOTO-017 — text is sized from one defined type scale

1. Every text element on the home page, the upload modal and the Larger view is
   sized at a step of the scale; no text carries a size from outside it.
2. The same kind of text element is sized at the same step on every view it
   appears on.
3. The steps are readable in one place, not inferable only from the result.
4. The token sheet lists five named steps — app bar title, section heading,
   body, small, caption — and the stylesheet names each as a token.
5. Text is set in a system font stack; no font file ships with the application.
6. Opening the page downloads no font file.

### REQ-PHOTO-018 — space is taken from one defined spacing scale

7. Every space between and around elements on those three views is a step of the
   scale; none is set by a value outside it.
8. The steps are readable in one place.
9. The space between adjacent tiles is the same across the Grid.
10. The token sheet states one base unit and a fixed set of multiples, each named
    as a token in the stylesheet.
11. The Grid's gap keeps the value it has today and becomes one of the steps.

### REQ-PHOTO-019 — an app bar carrying the product name

12. An app bar region is present and contains the product name as text.
13. At a desktop width it is visible without horizontal scrolling and overlaps
    neither the Grid nor the "+ Upload Photo" control.
14. It is present, with the same name, when no Photo is held.
15. It reads "Photo Gallery".
16. It scrolls away with the content; it is not fixed.
17. It carries the product name only; "+ Upload Photo" stays above the Grid.
18. The Larger view's overlay covers it.
19. Its surface is the white named on the token sheet, on the near-white ground.

## Approach

Everything here is CSS custom properties plus one markup element. No new
dependency, no build step, no font file — REQ-PHOTO-014@v1 and REQ-PHOTO-015@v1
are untouched, and answer 32 and answer 47 both turn on that staying true.

**`src/public/gallery.css`** grows a `:root` block that is the readable record
criteria 3, 8 and 10 ask for, and every hard-coded size and space in the file is
replaced by a reference to it. The file is 126 lines today and stays well inside
the 800-line limit. The tokens I propose:

```
--font-stack        system-ui, -apple-system, "Segoe UI", sans-serif   (as today)

--text-app-bar-title  1.25rem     (h1 keeps the size it has today)
--text-heading        1.125rem    (upload modal h2 moves 1rem -> 1.125rem)
--text-body           1rem
--text-small          0.875rem
--text-caption        0.75rem

--space-1  0.25rem     base unit
--space-2  0.5rem
--space-3  0.75rem
--space-4  1rem        <- the Grid gap, unchanged
--space-6  1.5rem
--space-8  2rem

--color-page     #f7f8fa   near-white ground
--color-surface  #ffffff   app bar, tiles, modal surfaces
--color-text     #1f2933   dark neutral
--color-border   #b0bec5   mid neutral (the modal border colour today)
--color-accent   #1565c0   single accent (the focus-ring blue today)
```

Two choices in that table are deliberate rather than arbitrary. `--space-4` is
1rem because `--gap` is 1rem today, and answer 49 says the Grid's gap keeps its
value and the scale is built *around* it — so the base unit is 0.25rem and 1rem
falls out as a multiple, rather than the gap being moved to fit a tidier scale.
`--color-accent` is `#1565c0` because that is already the focus-ring colour in
the file; reusing it means the accent and the focus ring agree without a second
decision.

The palette is listed in full because the token sheet must be, but this slice
*applies* only `--color-page` and `--color-surface`, which criterion 19 needs.
Text, border and accent are applied by slice 9 under REQ-PHOTO-020 and
REQ-PHOTO-021. Defining them now and using them later is what makes the sheet a
single approval rather than three.

**`src/home-page.js`** wraps the existing `<h1>Photo Gallery</h1>` in
`<header class="app-bar">`. The words are already on the page — answer 33
confirms them as the product name rather than introducing one — so this adds a
region, not content. The header sits in normal flow before `<main>`, which is
what makes criteria 13, 16 and 17 true without a rule: nothing is positioned, so
nothing can overlap and nothing can stick. Criterion 18 needs nothing at all: the
Larger view is a `<dialog>` opened with `showModal()`, so it renders in the top
layer, above the header, already.

No change to `src/server.js`, `src/store.js`, `src/photos.js`,
`src/public/lightbox.js` or `src/public/upload-modal.js`.

**Three new test files**, following the CSS-level pattern
`tests/responsive.test.js` established and its `ruleFor()` helper: read
`gallery.css` as text and assert on declarations. Answer 47 endorses exactly
this — token values named in the stylesheet, asserted by the existing test setup,
nothing rendered. I propose lifting `ruleFor()` into `tests/support/css.js` so
four files share one copy rather than each keeping its own.

Two existing assertions constrain what may be written, and the plan respects
both: `responsive.test.js` forbids any `width`/`min-width` of three or more
digits in px (everything above is `rem`), and forbids a `margin:` declaration on
`.tile` (spacing stays on the Grid's `gap`).

## Decisions this forces

**ADR-0001 — the design token sheet.** The values above are a proposal and
nothing more until KCB approves them. This is the deliverable answer 30 names,
it gates slices 8 and 9, and it is the single ADR this project has needed so far.
Write it with `/adr-write`, `Status: proposed`, `Governs: src/public/gallery.css`.
It should carry the full sheet — palette, typeface stack, both scales, radius,
focus ring and the two button variants — not only what this slice applies, so the
client approves once.

**Whether tests may read `.brain/`.** Four of the nineteen assert against
ADR-0001 rather than against `src/`. It is the only way I can see to make "the
token sheet lists the steps" checkable without a browser, but it couples the test
suite to the record, and no existing test does that. If you would rather it did
not, say so and I will drop those to criteria verified by the approval itself —
the count then falls to fifteen tests, and criteria 4 and 10 rest on the ADR
existing rather than on a test.

**Whether the h2 may move.** The upload modal's heading is `1rem` today and
`--text-heading` is `1.125rem`. Criterion 2 requires headings to share a step, so
either the h2 moves up or the scale gains a step that exists only to preserve it.
I propose it moves. It is a visible change to a delivered view, inside
REQ-PHOTO-017's scope, but you may prefer KCB to see it at the demo knowingly.

## What I am unsure about

**Criterion 1 is stronger than a test can be.** "Every text element is sized at a
step" is checkable in the stylesheet; it is not checkable that no element picks
up a size from a user-agent default that happens to differ. The tests assert that
the *stylesheet* names no size outside the scale, which is the honest reading and
is what answer 47 describes. A browser could still paint something the tests
would pass. This is the same gap `responsive.test.js` already records at its head,
and it is worth repeating in the new files rather than leaving implied.

**"Every space" in criterion 7 includes spaces nobody declared.** Line height,
the gap a `<p>` gets from the user agent, the dialog's own padding — none is set
by this stylesheet, so none can be drawn from the scale. I read the criterion as
governing the spaces the application sets, not every space that ends up on
screen. If you read it as the stricter thing, the work grows: a reset would be
needed, and that is a decision, not an implementation detail.

**Criterion 18 currently passes by accident.** `<dialog>.showModal()` puts the
Larger view in the top layer, so the app bar is covered without any rule being
written. The test I propose asserts the mechanism rather than the outcome, and
would keep passing if someone swapped the dialog for a positioned div and
happened to get the stacking right. I do not have a better check that avoids
rendering.

**The palette is half-applied by design, and that will look odd in review.**
This slice defines five colour tokens and uses two. A reviewer reading the diff
will reasonably ask why `--color-accent` is declared and unreferenced. It is
because the sheet is approved once and slice 9 consumes the rest; I would rather
flag it here than have it read as dead code.

## Rulings — KCB (developer), Sep-01-2026

Settled when `/tdd` was invoked against this plan and stopped at the token-sheet
gate. The three open questions above are closed as follows.

**The ADR comes first.** `/tdd` does not run until KCB has approved ADR-0001.
REQ-PHOTO-016@v1 criterion 4 is honoured rather than waived, and the ADR carries
the full sheet so slices 8 and 9 are unblocked in one round. The alternative —
build now and document afterwards — was considered and rejected: it inverts the
gate, and reworking the stylesheet and nineteen tests on a changed value is the
failure FB-0001 recorded.

**The four ADR-reading tests stay.** Criteria 017-4 and 018-10 are checkable
without a browser only by asserting against the token sheet itself. The suite
gains a dependency on `.brain/decisions/ADR-0001`, which no existing test has;
that is accepted deliberately, not overlooked.

**The upload modal's `h2` moves from `1rem` to `--text-heading` (1.125rem).**
Headings share a step, as criterion 2 requires. The scale keeps the five named
steps answer 48 asked for rather than gaining a sixth to preserve one element.
This is a visible change to a delivered view and KCB sees it at the demo.
