# Plan — REQ-PHOTO-003@v1, REQ-PHOTO-004@v1, REQ-PHOTO-005@v1

Written Sep-01-2026, on branch `feat/photo-upload-modal`. Slice 3 of
`.brain/slices.yaml`.

`REQ-PHOTO-004` depends on `003`, and `005` depends on `004`. Both dependencies
are inside this slice, so nothing here designs against a shape another slice has
yet to choose. Slice 2 is on this branch, so the Grid the modal opens over
already exists.

**Nothing is stored by this slice.** `REQ-PHOTO-006` (a submitted file becomes a
Photo) is slice 4. A file that passes every check here is *accepted* and then
discarded.

---

## The constraint that shapes this whole plan

Fifteen criteria, and most describe **browser behaviour**: a modal opening in
front of the page, focus moving with the keyboard, a file chooser that offers one
file. `REQ-PHOTO-015` permits a third-party dependency only where it "serves the
web server, SQLite access or image thumbnail generation". **A browser automation
tool is none of those**, so Playwright and every equivalent are excluded, and
`node --test` cannot drive a browser.

The honest consequence: **this slice cannot be fully verified automatically.**
The design below pushes as much behaviour as possible out of the DOM and into
pure functions that Node can test properly, and the remainder is asserted at the
markup level with the gap stated per test. Four criteria come out
**manual-only**. That is a real coverage hole, and section *What I am unsure
about* proposes what to do about it.

---

## What must be true

**REQ-PHOTO-003 — the control (3)**

1. A single activatable control bearing the text "+ Upload Photo" is on the home page.
2. It is present and activatable with no credentials supplied and no sign-in step.
3. It receives keyboard focus and can be activated from the keyboard.

**REQ-PHOTO-004 — the modal (5)**

4. Activating the control displays a modal in front of the home page, with the Grid still present behind it.
5. Activating it does not change the browser address and does not reload the page.
6. While an Upload is in progress, attempting to close the modal leaves it open, and the Upload continues to completion or failure.
7. The modal displays in current Chrome, Edge and Firefox on a desktop PC.
8. The modal's file-choosing and submit controls take keyboard focus and can be activated from the keyboard.

**REQ-PHOTO-005 — choosing a file (7)**

9. Choosing a file displays its name in the modal.
10. Submitting with no file chosen starts no Upload and leaves the Photo count unchanged.
11. Choosing a file that is neither JPEG nor PNG is rejected **in the browser**, with a message naming the accepted formats, and nothing is transferred.
12. A JPEG and a PNG are each accepted for Upload.
13. A file larger than 10 MB is rejected, a message states the 10 MB limit, and no Photo is created.
14. A non-accepted image submitted **directly to the server**, bypassing the browser check, is rejected on the basis of file content and type, and no Photo is created.
15. The file chooser offers exactly one file; selecting several at once is not offered.

---

## Approach

The decisions move out of the DOM. `src/upload-rules.js` holds the accepted
types, the 10 MB limit, the JPEG and PNG magic-byte signatures, and two pure
functions — `validateChosenFile({ name, type, size })` for what the browser can
see before sending, and `sniffImageType(bytes)` for what only the server can
check. Both the client and the server import the same module, so criterion 11 and
criterion 14 enforce one rule rather than two that can drift apart.

`src/public/upload-modal.js` is the client wiring, deliberately thin: open the
`<dialog>`, show the chosen file's name, call `validateChosenFile`, render the
message, disable dismissal while a request is in flight, POST. It contains no
rule of its own.

The modal is a native `<dialog>` opened with `showModal()`. That gives criteria 4,
5, 6 and 8 from the platform rather than from hand-written code: `<dialog>`
renders above the page with the Grid behind it, opening it navigates nowhere, and
it supports being made non-dismissable while a request is in flight.

`src/server.js` gains `POST /uploads`. It re-validates by content, and **stores
nothing** — on success it answers `202 Accepted` and creates no Photo, because
`REQ-PHOTO-006` is slice 4. The body is sent as raw bytes with `content-type` and
an `x-filename` header rather than as `multipart/form-data`: Node's standard
library has no multipart parser, and adding one would need a dependency
`REQ-PHOTO-015` does not obviously permit. Slice 4 may revisit that.

`src/home-page.js` renders the `<dialog>` and gives the existing "+ Upload Photo"
control its behaviour — the button slice 2 deliberately left inert.

| Path | Change |
|---|---|
| `src/upload-rules.js` | new — accepted types, size limit, magic bytes, two pure validators |
| `src/public/upload-modal.js` | new — client wiring, no rules of its own |
| `src/home-page.js` | changed — render the dialog, wire the control, load the script |
| `src/server.js` | changed — serve the script, add `POST /uploads` |
| `src/public/gallery.css` | changed — modal styling |
| `tests/upload-rules.test.js` | new — the pure rules |
| `tests/upload-modal.test.js` | new — markup and server behaviour |

## Test skeleton

Fifteen tests, one per criterion, each annotated `// @covers REQ-PHOTO-00N@v1`
for the requirement it belongs to. **The verification column is the point** — it
says what each test actually proves.

### `tests/upload-rules.test.js` — real behaviour, properly tested

```js
// @covers REQ-PHOTO-005@v1
test('rejects a file that is neither JPEG nor PNG, naming the accepted formats', ...)
  // validateChosenFile({name:'notes.pdf', type:'application/pdf', size:1000})
  //   → { accepted:false }, message matches /JPEG/ and /PNG/          [criterion 11]

// @covers REQ-PHOTO-005@v1
test('accepts a JPEG and accepts a PNG', ...)
  // both → { accepted:true }                                          [criterion 12]

// @covers REQ-PHOTO-005@v1
test('rejects a file larger than 10 MB and states the limit', ...)
  // size = 10MB+1 → { accepted:false }, message matches /10 ?MB/      [criterion 13]
  // size = exactly 10MB → accepted (the boundary is not off by one)

// @covers REQ-PHOTO-005@v1
test('rejects a non-image whose name and type claim it is an image', ...)
  // sniffImageType(Buffer.from('this is not an image')) → null        [criterion 14, unit half]
  // sniffImageType(<real JPEG magic bytes>) → 'image/jpeg'
```

### `tests/upload-modal.test.js` — server behaviour, real

```js
// @covers REQ-PHOTO-005@v1
test('server rejects a file bypassing the browser check, on content not name', ...)
  // POST /uploads, x-filename: fake.png, content-type: image/png,
  //   body = plain text → 4xx, and countPhotos() unchanged            [criterion 14]

// @covers REQ-PHOTO-005@v1
test('server rejects a body larger than 10 MB', ...)
  // POST /uploads with 10MB+1 → 4xx, countPhotos() unchanged          [criterion 13]

// @covers REQ-PHOTO-005@v1
test('submitting with no file starts no Upload', ...)
  // POST /uploads with empty body → 4xx, countPhotos() unchanged      [criterion 10]
```

### `tests/upload-modal.test.js` — markup level, weaker

Each of these asserts the served markup or script source. None drives a browser.

```js
// @covers REQ-PHOTO-003@v1
test('home page carries exactly one "+ Upload Photo" control', ...)
  // one <button> whose text is "+ Upload Photo"                       [criterion 1]

// @covers REQ-PHOTO-003@v1
test('the control is present with no credentials and no sign-in step', ...)
  // GET / with no credentials → 200, control present, no password field
  //                                                                    [criterion 2]

// @covers REQ-PHOTO-003@v1
test('the control is keyboard reachable and activatable', ...)
  // it is a real <button>, not a <div> with a click handler
  // no tabindex="-1"                                                   [criterion 3, weak]

// @covers REQ-PHOTO-004@v1
test('activating the control opens a dialog over the page, grid behind it', ...)
  // markup contains <dialog>; the grid is a sibling, not inside it
  // the script calls showModal(), not show() or a class toggle         [criterion 4, weak]

// @covers REQ-PHOTO-004@v1
test('opening the modal navigates nowhere and submits no form', ...)
  // the control is type="button" inside no <form> with an action
  // the script contains no location assignment and no form.submit()    [criterion 5, weak]

// @covers REQ-PHOTO-004@v1
test('the modal cannot be dismissed while an Upload is in progress', ...)
  // the script cancels the dialog's cancel event while in flight       [criterion 6, weak]

// @covers REQ-PHOTO-004@v1
test('the modal displays in current Chrome, Edge and Firefox', ...)
  // asserts only that nothing outside the baseline is used:
  //   <dialog> and showModal() are supported across all three
  // THE BROWSERS ARE NOT RUN                                           [criterion 7, manual]

// @covers REQ-PHOTO-004@v1
test('the file input and submit control are keyboard reachable', ...)
  // real <input type="file"> and <button>, neither tabindex="-1"       [criterion 8, weak]

// @covers REQ-PHOTO-005@v1
test('the chosen file name is displayed in the modal', ...)
  // the script writes the file name into a named element present in the markup
  //                                                                    [criterion 9, weak]

// @covers REQ-PHOTO-005@v1
test('the file chooser offers exactly one file', ...)
  // <input type="file"> carries accept="image/jpeg,image/png"
  // and does NOT carry the multiple attribute                          [criterion 15]
```

## Decisions this forces

1. **Client-side JavaScript enters the project.** Slice 2 chose server-side
   rendering; this slice adds a script. The pair of decisions is what slice 5
   (`REQ-PHOTO-008`, appear without a reload) will inherit, and they should be
   recorded together in one ADR rather than separately after the fact.
2. **Native `<dialog>` and `showModal()` rather than a hand-built overlay.** It
   buys four criteria from the platform, and it is a browser-support commitment.
3. **Raw body upload rather than `multipart/form-data`.** Chosen to avoid a
   dependency `REQ-PHOTO-015` does not clearly permit. Slice 4 stores the bytes
   and may find this the wrong shape.
4. **`POST /uploads` returns `202 Accepted` and stores nothing.** A route that
   accepts and discards is strange on its own; it is a slice boundary, not a
   destination.
5. **One rules module shared by client and server.** It is what keeps criteria 11
   and 14 from drifting into two different definitions of "an image".

---

## What I am unsure about

- **Four criteria are weakly covered and one is manual-only.** Criterion 7 (three
  named browsers) cannot be automated here at all — the test asserts only that
  nothing outside the common baseline is used, and the browsers are never run.
  Criteria 3, 4, 5, 6, 8 and 9 are asserted against markup and script *source*,
  not behaviour: they would pass against a script that reads correctly and
  malfunctions. **This is the weakest verification in the project so far, and it
  is the direct result of `REQ-PHOTO-015`.** The options are (a) accept it and
  verify by hand at the demo, (b) ask KCB to extend the approved dependency list
  to cover a browser test runner, which is a `/find-variation` question, or (c)
  keep the constraint and accept permanently manual UI verification. **This is
  the decision I most want from you.**
- **Criterion 6 says the Upload "continues until it completes or fails", but
  nothing completes in this slice.** With no store, "in progress" only exists
  between the POST and its 202. The test can only prove dismissal is blocked
  during a request that resolves immediately. It becomes properly testable in
  slice 4.
- **Criterion 12 says a JPEG and a PNG are "accepted for Upload" — accepted, not
  stored.** I read that as passing validation and reaching the server, which is
  all this slice can offer. If KCB meant stored, criterion 12 belongs in slice 4.
- **`202 Accepted` is my choice**, not the client's. Nothing in the record names a
  status code.
- **Criterion 11 requires rejection with "no data transferred to the server".**
  Testable in principle by asserting the server saw no request, but with no
  browser the test asserts the client module returns a rejection before its
  send path — again, source-level rather than observed.

## Approved — Sep-01-2026

The developer approved this plan as written, and answered the verification
question: **accept the gap and verify the UI by hand.**

`REQ-PHOTO-015` stands unchanged — no browser test runner is requested, and no
`/find-variation` is raised. This slice therefore ships with a **known and
accepted coverage hole**:

- Criterion 7 (Chrome, Edge, Firefox) is **manual-only**. The browsers are never
  run by any test in this repository.
- Criteria 3, 4, 5, 6, 8, 9 and 11 are asserted against **markup and script
  source, not behaviour**. They would pass against a script that reads correctly
  and malfunctions.

Anyone reading this later should know those tests do not mean what tests usually
mean, and that this was a deliberate choice rather than an oversight. The UI of
this slice is verified by a person at the demo or not at all.

Multipart was considered and not taken: the raw-body upload stands, so no parser
dependency is introduced.
